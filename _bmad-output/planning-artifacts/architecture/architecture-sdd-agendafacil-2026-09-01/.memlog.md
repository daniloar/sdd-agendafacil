- (decision) AD-1 PostgreSQL como store transacional canônico (não MongoDB). Binds: toda persistência de estado (slot, appointment, waitlist, penalidade, idempotência, eventos). Prevents: adotar document store sem transação multi-linha ACID de 1a classe e sem unique index parcial -> a garantia 'um slot = no máx. uma consulta confirmada' viraria lógica de app frágil e o double-booking volta pela camada de dados. Rule: estado canônico vive em Postgres; 'no máx. 1 confirmada por slot' é CONSTRAINT de banco (unique partial index em slot_id WHERE status='confirmed'), não checagem de app; Mongo não entra. Racional: Postgres dá (a) unique partial index como rede de segurança independente da corretude do código, (b) transação ACID multi-tabela para 'confirmar + sair da fila + gravar evento' atômico, (c) UPDATE ... WHERE status='free' com rows-affected = CAS otimista nativo sem lock pessimista. Mongo: transação multi-doc de 2a classe, unique parcial limitado, modelo incentiva embutir fila no slot -> contenção no mesmo documento.
- (decision) AD-2 Soft lock sem lock pessimista: CAS otimista em Postgres + marca de reserva com TTL em Redis. Binds: fluxo descoberta->held->confirmed; todos os cenários de concorrência do addendum. Prevents: SELECT ... FOR UPDATE segurando a linha do slot durante os 15 min de decisão (serializa atendimento, prende conexões, não escala) E dois pacientes confirmando o mesmo slot. Rule: (1) toda transição de slot é UPDATE slots SET status=?,... WHERE slot_id=? AND status=<esperado>, verificando rows_affected=1; 0 linhas = perdeu a corrida -> erro de domínio SlotUnavailable; nunca FOR UPDATE nem advisory lock bloqueante. (2) soft lock = (a) linha do slot vai a status='held' com held_by, held_until=now()+15min UTC via o CAS; (b) chave Redis slot:{id}:hold={patient_id} EX 900 como índice rápido e fonte de expiração proativa. (3) POSTGRES É A VERDADE; Redis é acelerador; em divergência held_until do Postgres decide. (4) expiração preguiçosa: qualquer leitura/transição que veja status='held' AND held_until<now() trata como free e faz CAS held->free antes de prosseguir; TTL do Redis + job do Sistema são só o caminho proativo. (5) confirmação = CAS held->confirmed WHERE held_by=? AND held_until>now(); falha por expiração no instante do submit cai em SlotUnavailable + oferta de fila. [ASSUMPTION] lock não-renovável na v1. [ASSUMPTION] coluna status+timestamps em vez de coluna version numérica genérica.
- (decision) AD-3 Redis para fila de espera e coordenação efêmera (não RabbitMQ). Binds: fila de espera, janela de aceite 30 min, fila VIP anti-starvation, expiração de soft lock, agendamento de lembrete D-1. Prevents: trazer um message broker para um problema que é de ESTADO ORDENADO CONSULTÁVEL e não de transporte; perder 'quem é o 3o da fila do slot X' dentro de um broker não-inspecionável. Rule: (1) fila por escopo = Redis Sorted Set waitlist:{scope}, score = prioridade composta (AD-4); ops ZADD/ZRANGE/ZREM. (2) oferta ativa (30 min) = chave Redis offer:{scope} EX 1800 + linha em Postgres waitlist_offers para auditoria e idempotência; expiração da chave -> Sistema avança para o próximo. [ASSUMPTION] 30 min contam da NOTIFICAÇÃO ENVIADA. (3) RabbitMQ/Kafka fora; fan-out de eventos de domínio para outros módulos (pagamento etc.) entra em Deferred, não agora. (4) [ASSUMPTION] Redis com appendonly yes (AOF) - a fila não pode evaporar num restart. (5) usar CAS nativo do Redis 8.4+ para transição de posse da oferta em vez de Lua quando der. Racional: fila é estrutura de dados ordenada que precisa de query por posição/remoção arbitrária/re-score; broker dá entrega e ordem FIFO cega, não isso.
- (decision) AD-4 Prioridade da fila e anti-starvation: score composto determinístico no Sorted Set. Binds: fila de espera, fila VIP. Prevents: dois builders ordenando a fila de formas incompatíveis (um por timestamp de entrada, outro por flag VIP) -> ordem não-determinística e starvation do paciente comum. Rule: score = função pura score(entry) = enqueued_at_unix_ms - vip_boost - age_promotion(waited); menor score atendido primeiro; vip_boost constante [ASSUMPTION 24h em ms]; age_promotion cresce com a espera de modo que após um teto [ASSUMPTION 48h] qualquer entrada comum ultrapassa um VIP recém-chegado. UMA fila, UM score - sem Sorted Set VIP separado. A função vive no domínio (hexágono), não em Lua no Redis; Redis guarda só o score calculado; re-score = ZADD idempotente. [ASSUMPTION] mecanismo = promoção por idade (não quota N:1): contínuo, sem contador com estado, teto de espera diretamente parametrizável.
- (decision) AD-5 Idempotência: chave obrigatória em toda mutação, registro em Postgres na mesma transação, resposta rejogada. Binds: confirmar, cancelar, aceitar vaga, entrar na fila, criar soft lock - toda escrita da API; e as automações do ator Sistema. Prevents: retry de cliente / duplo-clique / retry automático criando 2a consulta, 2a penalidade, 2a entrada na fila; cada endpoint inventando seu próprio dedupe. Rule: (1) todo POST/PUT de mutação exige header Idempotency-Key (UUID); ausente -> 400. (2) tabela idempotency_keys(key PK, request_fingerprint, response_status, response_body, created_at, expires_at); 1a vez processa DENTRO da mesma transação da mutação de domínio, grava a resposta, commita; repetição mesma key+fingerprint -> devolve resposta gravada, zero efeito colateral; mesma key + fingerprint diferente -> 409. (3) INSERT ... ON CONFLICT DO NOTHING com checagem de rows-affected serve de trava contra corrida de dois retries simultâneos (mesma disciplina de CAS do AD-2). (4) [ASSUMPTION] key expira em 24h; repetição após TTL vencido = tratada como nova. (5) automações do Sistema (expirar lock, avançar fila, disparar lembrete) derivam key determinística de (tipo, entidade, janela) ex. reminder:{appointment_id}:D-1 -> reexecução do job não duplica. [ASSUMPTION] idempotência de camada de aplicação, não exige exactly-once de infra.
- (decision) AD-6 Tempo em UTC, aritmética de janela no domínio via porta Clock. Binds: soft lock 15min, janela 30min, cancelamento <2h, lembrete D-1. Prevents: um builder calculando janela com hora local do cliente e outro com UTC -> bug de fuso nas 4 janelas; held_until gravado em local time. Rule: todo timestamp persistido é timestamptz em UTC; toda duração (15/30min, 2h, D-1) calculada no domínio a partir de uma porta Clock injetável (testável), nunca de hora do request; conversão para o fuso do paciente só no serializador da borda HTTP. [ASSUMPTION] D-1 = 24h antes do início da consulta; horário de disparo parâmetro da spec.
- (decision) AD-7 Estado do slot como máquina de estados explícita com caminho único de transição. Binds: all. Prevents: builders introduzindo transições divergentes (um permite confirmed->held, outro não) ou owners diferentes escrevendo slots.status. Rule: estados = free|held|confirmed|cancelled; transições legais = free->held, held->free, held->confirmed, confirmed->cancelled, cancelled->free ([ASSUMPTION] reabertura para a fila); toda transição passa por um único método de domínio Slot.transition(to, guard) que emite o SQL CAS do AD-2. SÓ o serviço de agendamento escreve a tabela slots; fila, lembretes e penalidade leem via eventos/queries e nunca escrevem o slot direto.
- (decision) AD-8 Eventos de domínio persistidos via outbox, consumidores idempotentes. Binds: avanço de fila (reage a slot liberado), agendamento de lembrete, registro de penalidade, auditoria. Prevents: fila e cancelamento disputando escrita no mesmo slot; automações acopladas por chamada direta; perder 'por que esse slot abriu'. Rule: toda transição de estado grava um evento na tabela outbox (slot_events) NA MESMA TRANSAÇÃO da mutação; um relay lê o outbox e publica em Redis (stream/pubsub) para os consumidores internos (avanço de fila, agendador de lembrete); consumidores são idempotentes (AD-5) e podem reprocessar. [ASSUMPTION] outbox em Postgres + relay simples, não CDC/Debezium nesta escala. [ASSUMPTION] política de retry/backoff do relay fica para a spec.

- (decision) AD-9 Autoridade e reconciliação da fila de espera. Binds: fila de espera, avanço de fila. Prevents: um builder tratando o Sorted Set do Redis como autoridade da fila e outro tratando a tabela waitlist_entry do Postgres como autoridade -> divergência de membros/ordem após restart do Redis, sem reconciliação (AD-2 resolveu isso só para o hold). - (decision) AD-4 RE-DERIVED per PRD FR-16..FR-18 (user chose PRD model over the pre-PRD composite score). Ordering: (1) strict class order VIP before comum; (2) within a class, order of entry (enqueued_at UTC). Anti-starvation = TWO mechanisms: (a) QUOTA - per waitlist a stateful counter of consecutive Offers granted to VIPs; after N (default 3, configurable) the next Offer goes to the first eligible comum, counter resets on ANY grant to a comum; (b) CEILING - a comum waiting longer than the ceiling (default 24h, configurable) gets max priority, ahead of VIPs. The composite score / vip_boost model from the old AD-4 is DROPPED. Ordering is a pure domain function evaluated at Offer-creation time over waitlist_entry rows + the queue's vip_grant_counter; deterministic (no tie broken by chance). Redis Sorted Set is now only a cache/index of the domain-computed next-eligible; the quota counter and ceiling logic live in the domain, counter persisted in Postgres (authority, AD-9).

- (decision) AD-11 (new) Immutable audit trail as a first-class, in-scope capability (PRD FR-27/FR-28). Implementation MAY use one shared append-only transitions table feeding both, or two tables written in the same tx - not fixed at this altitude, but 'same transaction as the mutation' is the invariant.
